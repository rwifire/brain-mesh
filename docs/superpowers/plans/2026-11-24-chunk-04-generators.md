# Chunk 4: Generators and `doctor --fix` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `doctor` reports out-of-date generated content (`links_to`, MOC lists, `CODEOWNERS`, the generated part of a brain's `AGENTS.md`, a missing `CLAUDE.md`), and `doctor --fix` regenerates it byte-identically on every platform, repairing generated blocks that hold merge-conflict markers.

**Architecture:** Every generator is a pure function from the loaded `WorkspaceModel` to a list of **planned files**: `{ code, brain, path, current, next }`, where `next` is the file's full intended text. One check turns each planned file with `next !== current` into a finding. `--fix` writes `next` for each of them, reloads the workspace and reports what is left. Block and conflict handling lives in one pure module, so MOC lists and `AGENTS.md` share it.

**Tech Stack:** Chunk 3 stack. `yaml`'s `parseDocument` edits `brain.yaml` without losing comments. No new dependencies.

**Spec:** [docs/spec.md](../../spec.md), sections 3 (Versioning: "depends only on the brain's `schema`"), 5.1, 5.2 (`links_to`), 5.4 (MOCs), 5.7 (CODEOWNERS), 6.3, 8 (`doctor [--fix]`, "also inside conflict markers"). [ADR 0001](../../adr/0001-generated-moc-lists-travel-in-each-pr.md). Breakdown: [v0-breakdown.md](../../plan/v0-breakdown.md), chunk 4 and "Moved from chunk 3". Chunk 3 plan for the model: [2026-11-22-chunk-03-doctor-checks.md](2026-11-22-chunk-03-doctor-checks.md).

## Global Constraints

- Everything from chunks 2 and 3 still holds:
  - the `--json` envelope;
  - exit codes 0 / 1 / 2;
  - findings with workspace-relative POSIX paths;
  - LF files;
  - commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Work on branch `chunk-04-generators` in the main checkout.
- Determinism, from ADR 0001: "Generator output must be deterministic and sorted, and depend only on the brain's `schema` version, never on the core version". In practice:
  - no timestamps;
  - no core version;
  - no filesystem order (sort with plain code-unit comparison, not `localeCompare`);
  - `\n` line endings in generated text.
- MOC marker lines are exactly `<!-- brain-mesh:index -->` and `<!-- /brain-mesh:index -->`, each on its own line (spec 5.4). The `AGENTS.md` block uses `<!-- brain-mesh:agents -->` / `<!-- /brain-mesh:agents -->`.
- MOC entry format, from the spec example: `- [Runner cache strategy](../areas/ci/runner-cache-strategy.md) — How we cache node_modules on CI runners`. The separator is space, U+2014 em dash, space.
- "`doctor --fix` generates a root-level `CODEOWNERS` from area owners" (shared brains only).
- `links_to` is "generated by doctor from outgoing links"; unmounted targets count (spec 6.3).

## Rulings in this plan

1. **Titles in MOC lists** are the humanised file stem: hyphens become spaces and the first letter is upper-case. `runner-cache-strategy` gives "Runner cache strategy", which matches the spec example. For `README.md` entries the title comes from the folder name; `notes/README.md` gives "Notes". Headings are not read, so editing a heading never churns lists.
2. **Entries are sorted by their link path** (code-unit order). A link path containing a space or parenthesis is written as `<path>`.
3. **Summaries** come from the note's frontmatter `summary`, if it is a string, with whitespace runs collapsed to one space. Without a summary, an entry is just `- [Title](path)`.
4. **Missing MOC files:**
   - `index.md` is always created;
   - `notes/README.md` is created only when `notes/` holds at least one note;
   - area READMEs, maps and projects are never created, because a summary or owner can't be invented. A missing area README stays `area-readme-missing`.
5. **A MOC without markers** gets the block appended after one blank line. **`AGENTS.md` without markers** gets the block prepended, followed by one blank line. A missing `AGENTS.md` is created holding only the block.
6. **CRLF files keep CRLF:**
   - generated text is built with `\n`;
   - the planner converts `next` to `\r\n` when `current` contains `\r\n`;
   - so a correct CRLF file is never reported as out of date.
7. **`read` mounts** are never planned. They are neither checked for generated content nor written by `--fix`, because their own contributors keep them current.
8. **Brains whose `schema` is above `SUPPORTED_SCHEMA`,** or whose manifest can't be recovered, are not planned.
9. **Conflict repair is deliberately narrow:**
   - **A generated block:** every conflict hunk that lies fully inside the block region is dropped with the block. A hunk that straddles the block boundary makes the file `generated-block-invalid` and leaves it untouched.
   - **`CODEOWNERS`:** the whole file is managed, so it is always regenerated.
   - **`brain.yaml`:** a hunk is removed only when every line on every side starts with `links_to:`. Any other conflict in `brain.yaml` stays a `manifest-invalid` error.
   - Curated text is never deleted.
10. **`links_to` is written in flow style** (`links_to: [brain-handbook]`) at the end of `brain.yaml`. An existing key keeps its position, and an empty list removes the key. A target brain id is taken as written, and only when it is a valid `BrainId` that differs from the brain's own id.
11. **`claude-md-missing` is fixable** (it creates `@AGENTS.md\n`). The existing `claude-md-invalid` is not fixable, because rewriting would discard the user's text.
12. **Finding objects gain `fixable: boolean`**, taken from the registry, and the docs table gains a `--fix` column.

## Review Focus

1. **Idempotent fixes:**
   - running `doctor --fix` twice changes nothing the second time;
   - the regenerated fixture has zero findings on Windows and on Linux (CI), so the output is byte-identical across platforms.

   *(Task 6 test `fix is idempotent`; the fixture runs in CI on both OSes)*
2. **A CRLF MOC file** with up-to-date content is not reported. When it is regenerated, it stays CRLF. *(Task 3 tests)*
3. **Conflicts that can't be repaired safely** are left untouched by `--fix`, and the finding remains: a conflict hunk that straddles a block boundary, or one in curated text. *(Task 1 tests; Task 6 case)*
4. **A `brain.yaml` with a schema header comment and inline comments** keeps every comment byte for byte when `links_to` is updated. *(Task 2 test)*
5. **`--fix` writes only where it should:**
   - never into a `read` mount;
   - with `[brain]`, only into that brain.

   *(Task 6 tests)*

### Task 1: Blocks and conflict hunks

**Files:**
- Create: `src/generate/blocks.ts`
- Test: `test/unit/generate/blocks.test.ts`

**Interfaces:**
- Produces:
  - `interface Hunk { start: number; end: number; sides: string[][] }`
    - `start` and `end` are 0-based line indexes of the `<<<<<<<` and `>>>>>>>` lines, inclusive;
    - `sides` holds the lines between the markers, split at `|||||||` and `=======`.
  - `conflictHunks(text: string): Hunk[]`
    - a marker is a line that starts with `<<<<<<<`, `|||||||` or `>>>>>>>`, or that equals `=======`, after any trailing `\r` is removed;
    - an unclosed `<<<<<<<` is not a hunk.
  - `type BlockResult = { ok: true; text: string } | { ok: false; reason: string }`
  - `replaceBlock(text: string, name: 'index' | 'agents', body: string, where: 'append' | 'prepend'): BlockResult`
    - `body` is the block content without markers, each line ending in `\n` (it may be empty);
    - the block region runs from the first open-marker line to the last close-marker line, counting marker lines inside conflict hunks;
    - the region is replaced by `open\n` + `body` + `close\n`;
    - every hunk fully inside the region disappears with it;
    - when there are no marker lines at all, the block is added per `where` (Ruling 5);
    - the result is `ok: false` when any of these holds:
      - a close comes before the first open;
      - only one kind of marker exists;
      - a hunk straddles the region boundary;
      - a marker line sits outside the region.
    - It works on `\n`-normalised text and returns `\n` text; the caller restores CRLF.
  - `stripLinksToConflicts(text: string): string`: removes every hunk whose lines all start with `links_to:` (Ruling 9).
  - `withEol(next: string, current: string | null): string`: converts to `\r\n` when `current` contains `\r\n`.

- [ ] **Step 1: Write the failing tests** (`blocks.test.ts`). `O`/`C` are the index marker lines.
  - **`conflictHunks`:**
    - `finds a two-way hunk`:
      - `'a\n<<<<<<< HEAD\nx\n=======\ny\n>>>>>>> b\nz\n'` gives `[{ start: 1, end: 5, sides: [['x'], ['y']] }]`;
      - a diff3 hunk with `||||||| base` gives three sides;
      - CRLF input gives the same result.
    - `unclosed is not a hunk`: `'<<<<<<< HEAD\nx\n'` gives `[]`.
  - **`replaceBlock`:**
    - `replaces the block body`: `` `# T\n\n${O}\n- old\n${C}\ntail\n` `` with body `'- new\n'` gives `` `# T\n\n${O}\n- new\n${C}\ntail\n` ``.
    - `empty body`: gives `` `${O}\n${C}\n` `` in place.
    - `append when no markers`: `'# T\n\ntext\n'` gives `` `# T\n\ntext\n\n${O}\n- a\n${C}\n` ``. Input without a trailing newline gives the same result.
    - `prepend when no markers`: `'## Mine\n'` with `'agents'` gives `` `<!-- brain-mesh:agents -->\nB\n<!-- /brain-mesh:agents -->\n\n## Mine\n` ``.
    - `heals a conflict inside the block`: `` `${O}\n- a\n<<<<<<< HEAD\n- b\n=======\n- c\n>>>>>>> x\n${C}\n` `` with body `'- a\n- b\n- c\n'` gives text with no `<<<<<<<` and the three entries.
    - `heals duplicated markers from both sides`: a hunk whose two sides each contain `O`, an entry and `C` gives a single block.
    - `refuses a straddling hunk`: `` `${O}\n- a\n<<<<<<< HEAD\n- b\n${C}\ncurated\n=======\n- c\n${C}\nother\n>>>>>>> x\n` `` gives `ok: false`.
    - `refuses close before open` and `refuses an open without a close`: both give `ok: false`.
    - `a conflict outside the block is kept`: a hunk in the text above the block is still in the output, byte for byte.
  - **`stripLinksToConflicts`:**
    - `removes a links_to-only hunk`: `'id: x\n<<<<<<< HEAD\nlinks_to: [a]\n=======\nlinks_to: [b]\n>>>>>>> y\n'` gives `'id: x\n'`;
    - `keeps other hunks`: a hunk with `owner:` lines is unchanged.
  - **`withEol`:** `('a\nb\n', 'x\r\n')` gives `'a\r\nb\r\n'`, and `('a\n', null)` gives `'a\n'`.
